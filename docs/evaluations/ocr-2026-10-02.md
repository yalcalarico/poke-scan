## Por qué Chandelure aún falla al reducir

La lectura `137/128` llega al backend. El OCR del encabezado también produce
`We » ETE AER from Lampent . ripe. on`. El extractor de pre-evolución espera
`Evolves from`: no reconoce esa línea dañada y Lampent queda como evidencia
positiva de nombre. El ranking devuelve Lampent con 0,97 y la carta correcta
`me55-137` con 0,93, en el cuarto puesto. Por lo tanto mejorar sólo el número
no cierra este caso: hace falta resolver cómo pesa la pre-evolución dañada
frente a una lectura corroborada del número impreso.

## Experimentos descartados

Se probaron dos pasadas extra del pie (original y grises, PSM6), parches de
bloques oscuros invertidos y bandas angostas de código con PSM6/7, grises y
limpieza de contorno. No aportaron números ni códigos correctos adicionales.
Las pasadas completas sumaron aproximadamente 1–2 segundos por foto; no se
incorporaron al runtime. En la banda de Chandelure PSM6 leyó `30Ce`, que no es
un código exacto del catálogo. No se flexibilizó la validación ni se dedujo
`30C` desde una coincidencia parcial.

Hay además dos restricciones estructurales en la ruta normal: el loader de
configuración retorna listas vacías cuando progresivo está apagado; y el
pipeline sólo llena `footerAttempts` en modo progresivo. El pipeline normal
lee los recortes numéricos, pero no usa esas lecturas para `setCode`. Habilitar
código requiere una decisión explícita de flujo y una comparación con ganancia
real; cambiar sólo el extractor no alcanza.

## Repetir las corridas

Desde `frontend/`, con el backend local disponible:

```sh
SCAN_REPORT_FILE=/tmp/ocr-baseline-api.json pnpm exec vitest run --config vitest.e2e.config.mts
```

Para preparar la aproximación de galería desde la raíz (la conversión BMP aplica
la orientación antes de reducir):

```sh
mkdir -p /tmp/ocr-gallery1200
for photo in IMG_4985 IMG_4986 IMG_4987 IMG_4988 IMG_4989; do
  sips -s format bmp /tmp/cards-full/$photo.png --out /tmp/ocr-gallery1200/$photo.bmp
  sips --resampleWidth 1200 -s format png /tmp/ocr-gallery1200/$photo.bmp --out /tmp/ocr-gallery1200/$photo.png
done
```

Luego desde `frontend/`:

```sh
SCAN_E2E_DIR=/tmp/ocr-gallery1200 SCAN_HIGH_RES_DIR=/tmp/cards-full SCAN_REPORT_FILE=/tmp/ocr-gallery-api.json pnpm exec vitest run --config vitest.e2e.config.mts
```

Ambos diagnósticos pasaron; su assertion verifica que exista resultado, no la
precisión del ID. Los conteos anteriores se verificaron sobre los IDs del JSON.
El chequeo completo del repositorio queda a cargo del coordinador después de
integrar los tres frentes. Esta entrega sólo agrega documentación/evidencia.
