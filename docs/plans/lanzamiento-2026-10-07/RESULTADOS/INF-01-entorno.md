## Restricciones de runtime que condicionan la decisión

- `backend/package.json` usa `onnxruntime-node` `1.30.0`. La tabla oficial ofrece binarios CPU preconstruidos para Linux x64 y Linux ARM64, además de macOS ARM64; no certifica la combinación actual de `node:22-alpine`, musl, Prisma, Sharp y Argon2. Para el primer candidato Linux conviene evaluar Debian/glibc en la arquitectura realmente contratada y registrar Node, arquitectura, libc, dependencias nativas y resultado de carga. El éxito local en macOS no cierra esa compatibilidad.
- El worker resuelve `SCANNER_MODEL` o `.scanner-models/dinov2-small-int8.onnx`, y `SCANNER_VISUAL_INDEX_DIR`, luego `SCANNER_INDEX_DIR` o `.scanner-index`. La metadata inspeccionada anuncia revisión `8b1f705a3a7f6f062f6bdd21986c1583d3ef105d`, `int8`, 384 dimensiones, `modelHash` anterior y `preprocessingHash` `8170121eafd1c4dd3122475255b0c6bb811cc598d38abcaf34ac9dd5ca483708`.
- El vector/modelo que requiere el servicio es pequeño frente a la carpeta completa: 23.31 MiB de ONNX y 164.53 MiB de JSONL/metadata necesarios en el estado medido. La carpeta completa mide 14.18 GiB porque también guarda las imágenes de referencia. El worker vigente no las carga. El artefacto read-only de producción debe incluir el modelo y los archivos de índice compatibles; no debe llevar al runtime las imágenes cacheadas por accidente.
- El Dockerfile actual copia el contexto completo en el stage `builder`, mientras `backend/.dockerignore` no excluye `.scanner-index` ni `.scanner-models`: el contexto local incluye un árbol de 14.18 GiB, de los cuales 14.02 GiB son imágenes. La etapa final copia `node_modules`, `dist`, `prisma` y `package.json`, pero omite `scripts/scanner-visual-worker.mjs`, `scanner-visual-engine.mjs`, `scanner-visual-index.mjs`, el modelo y el índice. El Compose de deploy tampoco habilita `SCANNER_VISUAL_ENABLED`. Por lo tanto, esa imagen no demuestra que el scanner de producción esté empacado ni listo. INF-02 debe resolver el recorte de contexto, los módulos `.mjs` requeridos y el montaje/copia inmutable de modelo e índice antes de que BE-03 pueda declarar scanner ready.
- La API serializa una inferencia por instancia y devuelve 503 al scanner cuando está ocupada. El límite del worker es 30 s; una petición fría puede inicializar ONNX y validar el índice antes de responder. La preparación de readiness no debe convertir la cola en una vía paralela ni asumir varias réplicas: cada proceso tendría memoria, índice y admisión independientes.
- DB y Redis de Compose son PostgreSQL 16 y Redis 7. La base del perfil deploy hoy vive en el volumen Compose; el puerto público del host está ligado a loopback en el perfil local, pero frontend/backend del perfil deploy se publican directamente en 3000/3001. Hay que agregar un gateway de una sola entrada antes de exponerlos.
