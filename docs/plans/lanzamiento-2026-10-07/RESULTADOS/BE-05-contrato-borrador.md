## Contrato propuesto de recuperación

Los dos endpoints serán públicos para poder recuperar sin sesión; en éxitos y errores llevarán `Cache-Control: no-store` y `Pragma: no-cache`. Requerirán `X-Session-Request: 1`, JSON y la validación actual de `Origin` cuando esté presente. Cookie/path/atributos/CORS existentes se conservan; frontend usa `credentials: include` y `skipAuth` sin refresh automático. Pedir un enlace nunca cambia contraseña, bloquea login, revoca sesiones ni invalida enlaces anteriores.

| Método / ruta propuesta | DTO mínimo y resultado |
|---|---|
| `POST /api/auth/password-recovery-requests` | Request `{ "email": "persona@example.test" }`; `202 { "message": "Recibimos tu pedido. Si corresponde y el envío puede completarse, vas a recibir instrucciones para recuperar el acceso." }`. Acredita recepción, no emisión/entrega. Mismo status/cuerpo/headers para email registrado/no registrado, incluyendo limitación por identificador, cupo de tokens y fallos de entrega. No devolver id, token, `accepted`, existencia, cupo restante ni estado de correo. |
| `POST /api/auth/password-recoveries` | Request `{ "token": "<secreto opaco>", "newPassword": "<contraseña>" }`; éxito `200 { "success": true }`, después del commit. No devuelve sesión ni token, ni auto-login. |

Todos los errores nuevos tendrán `{ "code": "<código>", "message": "<copy en español>" }`; sólo validación admite `fields` con nombres seguros (`email`, `newPassword`, `request`), sin valores ni objetos de class-validator. Es una forma futura que requiere espejo backend/frontend; no es el error actual de Nest/ApiError. DTOs usan whitelist: email válido de hasta 254 caracteres y normalización `trim().toLowerCase()` sin reglas de alias de proveedor; nueva contraseña string de 8 a 72 caracteres como [RegisterDto vigente](../../../../backend/src/modules/auth/dto/register.dto.ts#L15). La forma de JSON se valida antes de consultar cuenta/token; una contraseña inválida no consume enlace. Falta de token o token de forma/contenido inválidos se agrupan como enlace inválido, sin eco del valor.

| Situación | HTTP / code propuesto | Copy / acción que UX-04 debe resolver |
|---|---|---|
| Email/JSON/contraseña no cumplen DTO | `400 INPUT_INVALID`, `fields` seguros | “Revisá los datos ingresados.” Validación junto al campo; para clave explicar 8–72 caracteres. Corregí sin perder el enlace en memoria. |
| Token ausente, incorrecto, usado, vencido, revocado o versión anterior | `400 RECOVERY_LINK_INVALID` | “El enlace no es válido o venció. Pedí uno nuevo para continuar.” Mismo estado; no distinguir cuenta, uso, fecha o causa interna. |
| Header ausente u Origin no permitido | `403 SESSION_REQUEST_FORBIDDEN` | “No pudimos procesar el pedido desde esta página.” Volvé al flujo propio; sin reintento automático ni detalle de configuración. |
| Límite compartido de IP o admisión global | `429 RECOVERY_RATE_LIMITED` + `Retry-After` en segundos enteros positivos | “Esperá un poco antes de volver a intentar.” Esperá el header; nunca calcula el valor a partir de existencia/cupo de una cuenta/token. |
| Indisponibilidad general conocida antes de admisión (DB/limitador/infra) | `503 RECOVERY_UNAVAILABLE`, sin detalle interno | “No pudimos procesar el pedido ahora.” Solicitud: reintento manual. Cambio: tratá el resultado como incierto si no hay confirmación, intentá login con la clave elegida antes de pedir otro enlace. |
| Red, timeout, respuesta ausente/incompleta o 5xx inesperado | Sin HTTP fiable; estado local `RECOVERY_RESULT_UNKNOWN` (no es code emitido por API) | “No pudimos confirmar el resultado.” Solicitud: nuevo pedido manual sujeto a límites. Cambio: intentá login con la clave elegida; si falla, pedí otro enlace. No repetir POST automáticamente ni al montar/recargar. |
| Éxito del cambio | `200 { success: true }` | “Cambiaste tu contraseña. Iniciá sesión con la nueva clave.” Limpiar sesión de esta pestaña y ofrecer login. |

`503` de solicitud sólo se expone por una condición general previa a distinguir identidades, igual para ambas. Un fallo de emisión/commit específico del usuario o del transporte se absorbe en el mismo `202` genérico; el cliente no sabe si hubo token. El consumo puede devolver error técnico genérico sin describir el estado del token. Registrar sólo métricas/códigos internos mínimos sin email, token, contraseña, link ni body. Futuros middlewares, proxy y sinks deben comprobarlo: el documento no acredita hoy todos los logs.

### Emisión, reenvío y entrega incierta

Política técnica recomendada para este borrador: secreto de **32 bytes aleatorios** (256 bits), base64url sin padding (**43 caracteres**), sólo SHA-256 único en PostgreSQL. TTL inicial configurable **30 min** (1.800 s), para una interacción breve con margen de correo; es propuesta a ensayar con INF-01, no tiempo de entrega medido ni garantía productiva. Se permiten hasta **3 tokens activos por usuario**, sin evicción ni invalidación por un nuevo pedido. Todos caducan individualmente y todos se invalidan al cambiar clave/versión. Campos futuros mínimos: `id`, `userId`, `tokenHash`, `issuedAuthVersion`, `createdAt`, `expiresAt`, `usedAt`, `revokedAt`; pertenecen a un modelo nuevo, no al schema actual. No hay campo de secreto recuperable ni estado durable de entrega.

Antiabuso propuesto: admisión de **5 pedidos/IP/15 min**, **3 pedidos por identificador normalizado en ventana móvil de 1 h**, separación mínima de **60 s** por identificador y cupo global compartido de admisión; cifra global y capacidad se definirán en sandbox. Bucket del identificador con HMAC del email normalizado, TTL de 1 h desde la última actividad y secreto fuera de Git. Contar intentos admitidos, incluso sin cuenta o con entrega fallida; crear/aplicar el mismo bucket antes de buscar User, sin publicar sus límites ni `Retry-After`. Rechazos de cuota por identificador/cap de tokens responden `202`. La admisión global/IP se calcula para todos antes del lookup, nunca a partir de si habría correo; un límite de transporte sólo silencia envío con `202`. Limitador atómico compartido/fail-closed por indisponibilidad general, sin confiar sólo en memoria o en un Redis desconectado. Su soporte durable/distribuido es trabajo de implementación pendiente; no modifica ni reabre BE-07. Validación/consumo también requieren límite compartido por IP/global antes de hacer trabajo criptográfico, sin bloquear cuenta ni invalidar tokens tras fallos. No devolver señales del cupo por token/cuenta.

La ventana móvil permite como máximo 3 emisiones en cualquier intervalo de 30 min; además se verifica el cap de 3 bajo lock. No se borra el más viejo para abrir lugar. Si hubo commit pero el proceso cayó antes de enviar, el secreto se perdió y no puede reenviarse: **un nuevo pedido admitido después de 60 s genera otro secreto**, manteniendo válido el anterior hasta su propio vencimiento/reset. Si ya se usaron los 3 pedidos/hora o el cap está lleno, se debe esperar a que vuelva a haber presupuesto y lugar; 60 s no garantiza emisión ni permite saltar cuotas. Agotamiento malicioso puede demorar nuevos envíos, límite residual explícito de antiabuso; no cierra acceso existente, bloquea login ni inutiliza enlaces entregados. UX usa espera/reenvío genéricos sin afirmar “te mandamos otro” ni mostrar un contador basado en cuenta. No hay entrega garantizada/durable ni reenvío del mismo secreto.

Procedimiento futuro de emisión: resolver `userId` y versión observada sin guardar email en logs; crear el token dentro de una transacción con **lock User primero**, releer User/versión y contar tokens vigentes bajo ese lock. Si la versión cambió desde el lookup, la fila desapareció o (si se agrega posteriormente) la cuenta está bloqueada, no emitir y conservar respuesta genérica. Guardar hash, versión y tiempos antes del commit. Sólo después pasar el secreto a un puerto sandbox acotado **en memoria**, sin esperar entrega para responder ni añadir espera sólo a cuentas existentes. La generación/lookup/commit pueden tener distinta duración; se exige medir que no haya señal fiable de existencia, no igualdad matemática de latencia. La admisión/capacidad debe aplicarse también a pedidos sin cuenta para evitar que la cola exponga existencia. No introducir una respuesta particular por fallo de inserción/envío de una cuenta.

El puerto debe descartar secreto/destinatario al terminar, fallar o vencer; no escribir cola/outbox, archivos, logs, trazas, body de correo ni evidencia de Git. Sandbox sin red de entrega real, con receptor sintético efímero y direcciones `example.test`; INF-01 debe aportar esa configuración antes de probar. No hay proveedor/remitente acreditado. Una cola durable con token plano o cifrado contradice “sólo hash” y requiere otro contrato; no se promete en éste. Antes de enviar puede comprobar vigencia y suprimir un enlace ya invalidado; una carrera aún puede entregar un enlace viejo que el consumo rechazará.

El link propuesto apunta al frontend `/recuperar#token=...`, nunca al API. GET/preview/apertura/montaje no consumen, validan contra API ni generan reenvío; sólo POST explícito de cambio consume. Leer fragmento una vez en memoria y quitarlo con `history.replaceState` antes de analytics/terceros, sin copiarlo a query, logs, storage, analytics o Git. Si recargar pierde el token, volver a abrir el link del correo o pedir uno nuevo; no persistirlo para resolver esa pérdida. FE-04 deberá garantizar que el arranque no exponga el fragmento antes de quitarlo, revisar Referrer-Policy/CSP y exclusión de caché del flujo. Son adaptaciones futuras; no se acreditan hoy por tener un fragmento.

### Consumo, sesiones y concurrencia

**Recomendación elegida para UX-04: revocación con `User.authVersion` y consulta a Postgres en cada autorización.** Versión entera no negativa, inicial 0, claim `authVersion` en JWT nuevos; guard compara existencia de User y versión actual con una selección privada mínima. Postgres es la autoridad, sin caché de versión que retrase la revocación. Si la DB no está disponible, fallar cerrado con error técnico genérico; no volver al guard actual. Costo/latencia deben verificarse antes de implementar. La opción de revocar sólo refresh y esperar access TTL (default configurable 15 min) queda como tradeoff descartado para este borrador: no es un contrato simultáneo ni requiere permiso humano nuevo para elegir esta recomendación rutinaria.

Transición legacy propuesta: cutoff de emisión fijo `legacyAccessCutoff` acordado para todas las instancias al desplegar. JWT firmado sin claim se interpreta como versión **0** sólo si `iat` válido es anterior al cutoff, `exp` válido no venció y User existe con versión 0. Ausencia/malformación de `iat`/`exp`, claim malformado o token sin claim emitido desde cutoff se rechazan. Reset incrementa versión, así que legacy 0 queda rechazado desde el commit. No usar “una versión del TTL actual” como fecha de retiro: el TTL histórico pudo ser otro. Antes de retirar compatibilidad, inventariar límites de `exp` históricos o decidir cierre forzado; sin evidencia, conservar sólo esta compatibilidad acotada por versión/cutoff y expiración individual. No se midió un máximo histórico ni configuración efectiva. Esta transición debe verificarse; no presupone que todos los JWT antiguos cumplan los campos exigidos.

Orden obligatorio común para emisión, consumo, refresh y eventual supresión: **User → filas de recuperación/refresh relacionadas**; nunca bloquear token y después User. Se puede lookup del hash fuera de transacción para localizar propietario, pero esa lectura no autoriza. Dentro de la transacción, bloquear User, releer User/versión y token por hash + `userId`; validar no usado/no revocado, `issuedAuthVersion` igual a versión vigente y `expiresAt` estrictamente posterior al reloj de DB leído **después de adquirir los locks** (no un `now()` de comienzo de transacción que quedó viejo mientras esperaba). Password hash puede calcularse antes del lock; autorización y vigencia siempre se releen dentro. Un token inexistente produce el mismo error genérico sin mutación.

Una sola transacción actualiza `passwordHash`, marca el token usado, revoca **todos** los otros tokens de recuperación y refresh del usuario e incrementa `authVersion`; rollback revierte todo. Dos consumos, aun de tokens distintos, dan exactamente un éxito: el segundo observa uso/revocación/versión. No emitir sesión en recuperación. Cookie `pcs.refreshToken` se limpia sólo en la respuesta posterior a commit exitoso, con atributos/path actuales; FE limpia access en memoria, pista y estado del AuthProvider sólo tras éxito confirmado. Ante `400`, `429`, `503` o resultado incierto no anunciar cambio ni limpiar sesión como si hubiera éxito. Si se perdió la respuesta tras commit, el guard/refresh previos fallarán aunque el browser conserve cookie: intentar login con la clave elegida, o iniciar pedido nuevo si falla; ningún POST de cambio se repite automáticamente.

Login futuro puede verificar Argon2 antes del lock para acotar retención del lock, pero deberá releer bajo lock el hash exacto que verificó y la versión observada; si cambió, rechazar credenciales sin crear refresh/JWT usable. Alternativa equivalente: revalidar la contraseña contra hash vigente bajo lock. La firma de JWT con versión vigente y creación del refresh pertenecen a la transacción de emisión bajo User, después de esa comprobación; no aceptar `PublicUser` previamente leído como autoridad. Refresh relee su fila/vigencia/revocación y User bajo el mismo orden; registro también debe usar User vigente al emitir. Así un login validado con clave vieja antes del reset no puede emitir un refresh usable después del commit. Una emisión confirmada antes del reset queda revocada por éste, aunque su respuesta llegue después.

Una solicitud de enlace que capturó versión anterior no puede emitir un token válido tras reset: el chequeo bajo User debe descartarla. Si emitió antes del reset, queda invalidada junto con todos los tokens al reset. Si su primera observación de User ocurre después del commit, pertenece a la nueva versión; no se promete cancelar toda solicitud pública por su hora de inicio HTTP. La misma distinción rige entregas diferidas de correo. La frontera del guard es su lookup de autorización: una autorización consultada después del commit rechaza JWT viejo; requests que ya pasaron el guard pueden concluir en vuelo. El control de sesión no cancela efectos ya autorizados ni promete borrar pantallas de otros dispositivos; UX debe comunicar nueva clave y reautenticación, con ese límite.

## Eliminación de cuenta: procedimiento preparatorio y decisión abierta

NEG-03 no exige endpoint en esta etapa. Su elección no bloquea el diseño de recuperación UX-04. El procedimiento futuro debe recibir una solicitud por la vía que NEG-03/owner elija, verificar titularidad mediante sesión y reautenticación reciente (o control equivalente del procedimiento), explicar alcance irreversible, confirmar explícitamente, ejecutar supresión, comprobar resultado y confirmar cierre. Canal, operador, plazos, autorización operativa, retención y auditoría mínima siguen sin decidir; este texto no asigna personas ni habilita borrar cuentas. No aceptar ID ajeno en body como autoridad; mantener ownership en `where`.

Si se elige autoservicio, propuesta separada a revisar: `DELETE /api/account` autenticado con confirmación y reautenticación. `200 { success: true }` sólo después de eliminación atómica; `202 { status: "pending" }` sólo si existe un estado durable de supresión ya modelado/probado que impida nuevas sesiones, recuperación, refresh, autorizaciones, escrituras y lectura pública. Definir idempotencia y consulta segura de estado antes de implementar; hoy no hay ese estado ni esos endpoints. La cookie de `/api/auth` no acompaña automáticamente `/api/account`; autenticación/reautenticación se diseñan expresamente, y limpieza compatible sólo tras commit de aceptación/supresión. Un `202` no significa borrado completado.

El límite para retirada activa es el commit atómico de eliminación o el commit del bloqueo durable, según la vía elegida. Antes: capturar sólo identificadores de claves de caché conocidos, sin loguear slugs secretos. Bajo lock User primero: retirar/inactivar links en origen, revocar refresh/recuperaciones/version y retirar perfil, colecciones/ítems/notas, amistades en ambos sentidos, snapshots, operaciones de adición, ScanJob y demás relaciones personales. Cascadas del schema deben comprobarse con migraciones/fixtures; no bastan como evidencia de ejecución. Preservar cartas, sets, precios, IDs externos, `PriceRefreshJob`, `ProviderRateLimit` y `SyncState` globales. No cancelar cola compartida al retirar tracking personal.

Para el futuro estado pendiente, guard/login/refresh/recuperación/lectura pública deben comprobarlo en Postgres; consultas a ShareLink activo por sí solas no cubren un estado nuevo de User. Los escritores personales que deban quedar bloqueados después del commit necesitan el mismo lock/estado y ownership dentro de su transacción, no sólo un guard previo. El flujo de supresión debe verificar que ninguna escritura iniciada antes repueble datos después del límite; se ordenan por User: las confirmadas antes pueden concluir, las que toman lock después rechazan. Esto es requisito futuro, no propiedad probada de los servicios actuales. Solicitudes de lectura que ya pasaron la comprobación pueden terminar en vuelo. Desde una nueva lectura de origen posterior al commit no habrá payload/metadata protegido por API/SSR; validar origen antes de caché y purgar claves conocidas como best-effort. No prometer cancelación ni retractación de respuestas, previews, memoria, CSVs o capturas ya descargados.

Backups requieren procedimiento separado: registrar supresión mínima independiente del snapshot o un paso controlado de aplicación posterior, elegido por INF-01/INF-03/owner, con acceso/integridad/retención definidos y sin email, credenciales o links secretos. Restaurar en entorno aislado, aplicar supresiones antes de habilitar tráfico y comprobar cuentas/links/sesiones/escrituras; una copia anterior no puede ser autoridad suficiente para reactivar. Diseño y ensayo están pendientes. No afirmar borrado físico de backups ni cumplimiento normativo; destino, frecuencia, responsable, acceso, retención y operación off-host no fueron elegidos. Copias descargadas por usuario/terceros salen del control del servidor.
