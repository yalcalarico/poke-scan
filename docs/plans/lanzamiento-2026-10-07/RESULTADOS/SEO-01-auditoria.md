# SEO-01 — Auditoría documental de indexación y soft 404

**Estado:** fase documental revisada y aceptada con correcciones Sol HIGH; SEO-01 sigue abierto hasta completar la matriz HTTP y verificar el dominio real.
**Responsable:** Codex · **Fecha:** 2026-10-08
**Alcance de esta fase:** lectura de fuentes actuales y documentación instalada de Next.js; sin cambios de aplicación ni solicitudes HTTP a la aplicación.

## Resultado

La política en código es acotada en el sitemap: solo declara `/`, `/buscar` y `/faq`. La landing y FAQ tienen canonical propio; búsqueda fija el canonical en `/buscar`, por lo que sus consultas/filtros no generan canonicals distintos. Las fichas válidas declaran canonical por ID y omiten `returnTo`; las fichas ausentes ejecutan `notFound()`. Los layouts de autenticación y varias páginas privadas declaran `noindex`; la ruta share también lo declara para recursos vigentes y ausentes, y no aparece en el sitemap.

El riesgo que no se puede cerrar con lectura estática es el dominio: `NEXT_PUBLIC_SITE_URL` cae por defecto en `https://pokescan.app` en metadata, `robots` y sitemap. El plan operativo conserva el dominio real como entrada pendiente. Hasta confirmar el valor de despliegue y consultar el dominio servido, no se puede afirmar que los canonicals/sitemap publicados apunten al dominio correcto.

La ficha inválida llama `notFound()` después de buscar la carta. La documentación instalada de Next.js 16.3.6 indica que `notFound()` agrega `noindex`; si la respuesta ya empezó a transmitirse, Next la termina con HTTP 200 y la marca `noindex`, mientras que sin streaming puede responder 404, como explica la [referencia oficial not-found](https://nextjs.org/docs/app/api-reference/file-conventions/not-found). El `noindex` protege la indexación del caso ausente, pero no prueba que el deployment haya contestado 404. El código y la documentación permiten describir ambos resultados; no medí cuál ocurre para esta ruta. Para cerrar la aceptación, hay que consultar una ficha inexistente en el despliegue acordado y guardar status, headers y HTML inicial/completo.

Hay `loading.tsx` en ficha y share, por lo que existe una frontera de streaming real en las fuentes; eso no determina el status de cada request. Además, [`generateMetadata` puede transmitir las etiquetas después de la UI inicial y anexarlas al body](https://nextjs.org/docs/app/api-reference/functions/generate-metadata#streaming-metadata). Next documenta lectura del DOM completo para Googlebot y metadata bloqueante en head para bots limitados a HTML. La medición debe distinguir head inicial, etiquetas del documento completo y DOM renderizado por user-agent; no declarar metadata ausente solo porque no estaba en el primer chunk.

## Hallazgos y decisiones mínimas

1. **P1 — Host de publicación pendiente.** La misma variable pública determina metadata base, sitemap y robots. El fallback literal es `https://pokescan.app`; no hay evidencia de que sea el host aprobado/productivo. **Dueño:** INF-01/operación debe confirmar el dominio y valor de despliegue; SEO/Frontend revisa la salida publicada después. No reemplazarlo con otro host supuesto.
2. **P1 — Status de ficha ausente no medido en deployment.** La aplicación expresa ausencia mediante `notFound()`; Next documenta 200 con stream y 404 antes del stream, y `noindex` en ambos caminos. No hay defecto de código confirmado ni HTTP actual observado. **Dueño:** SEO documenta status/señal y propone exports mínimos si fallan; una solución que mueva fetch, fronteras de render o tratamiento de errores requiere handoff frontend, y proxy/hosting corresponde a infra. HTTP 200 con noindex no es por sí solo un bug confirmado ni obliga a cambiar streaming.
3. **P2 — Búsqueda dinámica con canonical común.** Las consultas convergen a `/buscar`; el HTML del servidor incluye shell/fallback y la carga de resultados ocurre en cliente según el plan. No se midió render de crawler. El canonical es una señal para consolidar URLs, no una prueba de que los resultados tengan contenido rastreable.
4. **Control positivo de indexación.** Auth, superficies de app/cuenta inspeccionadas y share tienen noindex en metadata; sitemap está limitado a tres URLs públicas. Esto no acredita privacidad ni autorización: esas garantías dependen del contrato público, ownership, auth y cachés FE/BE. La presencia final de las directivas debe verificarse en la respuesta servida. `robots.txt` permite el rastreo general y no sustituye `noindex`; [Google advierte que bloquear el rastreo impide leer noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing).
5. **No ampliar el sitemap con fichas en esta tarea.** El SEO-02 ya requiere un conjunto de fichas válidas y publicadas, costo y descubrimiento medidos. Esta auditoría no habilita indexación masiva, generación de páginas ni nuevas consultas al catálogo.

## Checklist para la medición HTTP posterior

La matriz HTTP/SSR/DOM **local no depende de INF-01 ni de un dominio productivo**: puede ejecutarse con host sintético autorizado, IDs/slugs de fixtures propias y una ventana runtime aislada acordada con coordinación. Registrar origen/base configurados del entorno local y no atribuir sus resultados a producción. La comprobación del canonical/sitemap **en producción** es una fase separada que sí necesita dominio aprobado y valor efectivo de despliegue. La ejecución necesita host, ruta exacta, fecha, user-agent y resultado sanitizado; nunca registrar tokens, cookies, email, slug de usuario real ni URLs de cuenta.

1. Solicitar HTML público sin cookies en desktop/mobile user-agent normal; registrar URL final tras redirecciones, status, `Content-Type`, `X-Robots-Tag`, canonical, meta robots, title/description y OG. Extraer por separado head inicial y etiquetas del documento completo (incluido body transmitido); anotar duplicados o contradicciones, sin inferir el status desde el texto de UI.
2. Repetir con Googlebot Smartphone solo si el entorno de producción acordado permite esa prueba; comparar HTML inicial y renderizado, sin usarlo como evidencia de indexación.
3. En búsqueda, usar query vacía, una consulta representativa y filtros finitos acordados. Anotar canonical, contenido de HTML previo a JS y DOM tras hidratación; no recorrer combinaciones.
4. En carta, comparar ID válido e inexistente. Verificar status, `noindex` en ausente, metadatos del válido y canonical sin `returnTo`. Distinguir respuesta 404 del backend de la respuesta HTML de Next.
5. En privado/share, usar identidades y datos sintéticos autorizados; verificar noindex y ausencia de contenido privado en ausencia/revocación/vencimiento, también en Flight/metadata. DEC-02 permite Next200 genérico por streaming: registrar ese resultado sin inventar Next404; verificar API404/no-store por separado. No reutilizar slug o colección humana.
6. Revisar `/robots.txt` y `/sitemap.xml`: status, URLs absolutas y solo landing/buscar/FAQ mientras SEO-02 no tenga aprobación separada. En local, contrastar contra la base sintética configurada y documentar status real; en producción, verificar además host aprobado/HTTPS y que el fallback no haya quedado publicado. Un resultado local correcto no cierra la comprobación productiva.
7. Guardar un JSON pequeño con valores de cabeceras/metadata sanitizados, origen inicial/completo/DOM de cada etiqueta y hashes de artefacto. Inspeccionar el documento en memoria y conservar solo los campos necesarios; no guardar páginas de cuenta, contenido completo de colección, credenciales ni cookies.
