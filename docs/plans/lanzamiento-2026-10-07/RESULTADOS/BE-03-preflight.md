## Propuesta mínima para revisión

- Conservar `GET /api/health` como liveness HTTP 200, incluido Redis degradado, porque es el probe persistente de Docker. La futura configuración de liveness puede seguir apuntando allí.
- Agregar una ruta separada de readiness para infraestructura, probablemente `GET /api/ready`, que devuelva 200 cuando la política acordada permita recibir tráfico y 503 si DB no está disponible o si el scanner habilitado no está disponible/compatible. El nombre, cuerpo y condición exactos quedan sujetos al handoff INF-01 y revisión Sol HIGH.
- Exponer estados explícitos y acotados: DB `ready|unavailable`; scanner `disabled|unknown|ready|unavailable|incompatible` (o equivalentes acordados); busy como dato informativo; Redis solo como `degraded` informativo. Si el flag del scanner está apagado, informarlo como `disabled`, no como `available` ni como error fatal de proceso. Redis no debe convertir liveness a 503; decidir si afecta readiness según política operativa, porque los flujos actuales tienen fallback.
- Restringir la información pública a estado, componente y quizá versión/hash opaco. No devolver paths, URL/secretos, mensajes de excepción, stack ni datos del usuario. `RedisStatus` ya da el patrón de superficie segura.
- DB: usar una consulta mínima real (p. ej. `SELECT 1`) solo en la ruta ready, con timeout efectivo y corto acordado con INF-01. Confirmar cómo establecer límites del driver/servidor y no confiar en `Promise.race` como cancelación. Si DB no está conectada al primer arranque, el comportamiento de startup de Prisma puede impedir que la ruta llegue a contestar; INF-01 debe decidir si eso se resuelve con política de restart/health de infraestructura o con un cambio acotado en startup.
- Scanner: el handler no debe iniciar child process, cargar ONNX, calcular hash completo, recorrer JSONL, indexar, descargar ni inferir. Para un estado veraz en frío hace falta una fuente barata que ya venga validada (por ejemplo, metadata/manifiesto de packaging con digest esperado) o estado validado y cacheado por un ciclo único fuera del probe. Hasta elegir una de esas fuentes, `unknown` debe impedir afirmar ready cuando el scanner está habilitado. No modificar el worker para crear un segundo camino de reconocimiento.
- Bound de HTTP: acordar con INF-01 timeout de respuesta/readiness y frecuencia de sondeo. El probe no debe amplificar consultas lentas a DB; considerar caché muy breve del último resultado solo si el margen de detección queda especificado. Responder 503 únicamente desde readiness, nunca desde el liveness persistente actual.
- No parece necesario agregar DTO en `frontend/types/api.ts`: no se encontró consumidor frontend de health/readiness y la ruta sirve a infraestructura. Si INF-01 detecta un consumidor de aplicación real, el dueño del contrato debe reservar y actualizar el espejo conforme AGENTS.md §1.

## Pruebas y aceptación para la implementación futura

- Unitarias rápidas y con dependencias mockeadas: DB sana/caída/timeout; scanner apagado; scanner habilitado frío/unknown; compatible; índice ausente/incompatible; busy informativo; Redis caído sigue liveness 200 y se informa degraded; ningún path/secret/mensaje privado en payload.
- Verificar explícitamente que invocar repetidamente readiness no llama `fork`, `InferenceSession.create`, `expectedMetadata`/hash, `refreshIndex`, lectura del JSONL, descarga ni inferencia. El probe DINO debe ser lectura de estado cacheado/metadata de packaging.
- E2E aislado: ruta de ready devuelve 200/503 con status HTTP y payload esperados; `/api/health` conserva 200 con Redis no disponible. Incluir escenario de DB caída después de arranque y documentar limitación si DB caída antes de bootstrap impide que la app escuche.
- Futuro flujo real en stack descartable, solo al cerrar el lote y según orquestación: probar scanner habilitado con modelo/índice de artefactos compatibles e incompatibles y DB/Redis aislados; jamás usar datos del usuario ni llamar proveedores de precio. El preflight no ejecutó ni afirma estas verificaciones.
- Aceptación ya escrita en BE-03: app sin DB no ready; índice ausente/incompatible explícito; Redis caído degrada sin matar proceso; scanner deshabilitado informado sin fingir disponibilidad; tests rápidos sin proveedores. La política final para `unknown` y el inicio sin DB se cierra con INF-01 antes de implementar.

## Estado de salida del preflight

Readiness requiere un endpoint distinto para separar DB/scanner de liveness; existe un patrón actual de estado Redis seguro, pero no existe hoy una fuente barata capaz de certificar compatibilidad DINOv2 en frío. Las decisiones de cold readiness, timeout de DB y consumo de probes quedan pendientes de INF-01 revisado. No se implementó código, no se corrieron tests/benchmarks, no se iniciaron procesos ni stack y no se accedió a DB/Redis/proveedores.
